# Nailbot — Data Migration & Architecture Improvement Plan

## Цель
Довести проект до "идеального состояния" с точки зрения долгосрочного хранения данных, чтобы была возможность качественно анализировать историю клиентов, записи, отзывы и карточки с помощью ИИ (включая еженедельные аналитические отчёты).

## Основные проблемы (приоритизировано)

| Приоритет | Проблема | Почему критично | Текущий статус (на момент создания плана) |
|-----------|----------|------------------|------------------------------------------|
| **P0** | Двойное хранение + отсутствие чёткого Source of Truth | Данные живут одновременно в старом StateStore и новой SQLite. Высокий риск расхождений и потери данных. | Частично решено |
| **P1** | Отсутствие стратегии миграции исторических данных | Вся существующая история находится только в Redis. При потере Redis данные исчезнут. | Не решено |
| **P2** | Неполное покрытие записи в новую БД | Не все важные изменения клиентских данных попадают в репозитории. | Частично |
| **P3** | Слабая аналитическая прослойка | Недостаточно удобных и богатых методов чтения для подготовки данных под LLM. | В процессе |
| **P4** | Сильная связанность кода со старым StateStore | handlers и main напрямую читают/пишут сырые словари состояния. | Серьёзная проблема |
| **P5** | Недостаточная наблюдаемость и надёжность долгосрочных данных | Отсутствуют бэкапы SQLite, мониторинг, алерты, стратегия восстановления. | Слабо |
| **P6** | Риск при dual-write переходном периоде | Нет чёткого правила, что считается правдой во время миграции. | Неявное |
| **P7** | Отсутствие тестов и безопасных точек отката | Большой рефакторинг без защиты. | Отсутствует |

## Порядок работы (по приоритету)

1. **P0 + P6** — Определить чёткую политику Source of Truth на переходный период + завершить покрытие записи.
2. **P2** — Довести покрытие записи важных сущностей до ~100%.
3. **P1** — Спроектировать и реализовать миграцию исторических данных.
4. **P3** — Развить аналитический слой до пригодного для реальных LLM-отчётов.
5. **P4** — Постепенно снижать зависимость от старого state_store (самая большая работа).
6. **P5 + P7** — Observability, бэкапы, тесты.

## Текущая политика Source of Truth (Transition Period)

**Дата обновления:** [будет обновляться]

### Правила на переходный период:

1. **Новые бронирования** (с момента внедрения) — **источник правды** = SQLite (`BookingsRepository`).
2. **Карточки клиентов** и их изменения — **источник правды** = SQLite (`ClientsRepository`).
3. **Отзывы и оценки** — **источник правды** = SQLite.
4. **Диалоговое состояние** (текущий шаг записи, корзина услуг и т.д.) — остаётся в Redis (`DialogStateStore`).
5. **Старые данные** (созданные до внедрения новой БД) — пока считаются в старом `state_store`. Мы их постепенно мигрируем.

### Во время перехода:
- При записи важных сущностей пишем **в оба места** (dual-write) с try/except на новую БД.
- При чтении для бизнес-логики (мой записи, отмена и т.д.) — пока используем старый state (для стабильности).
- При чтении для аналитики и новых фич — используем новую БД.

**Цель переходного периода:** постепенно сдвигать "правду" в сторону SQLite, пока старый StateStore не останется только для диалогового состояния.

## P1: Миграция исторических данных (следующий приоритет)

### Цель
Перенести все существующие данные клиентов (карточки + история записей + отзывы + реферальные данные) из старого `StateStore` (Redis + память) в новую SQLite.

### Проблема
- Вся история, накопленная до внедрения новой БД, существует **только** в Redis.
- При потере Redis, переезде, или очистке — вся прошлая история будет потеряна.
- Это прямо противоречит главной цели пользователя: "хранить историю записей, карточки, отзывы как можно дольше для AI-анализа".

### Предлагаемая стратегия миграции

**Подход: One-time + Idempotent Migration Script**

1. **Режимы работы скрипта**:
   - Dry-run (только показать, что будет перенесено)
   - Full migration (перенос всех данных)
   - Per-user migration (для отладки)

2. **Логика миграции**:
   - Брать всех пользователей из `nailbot:all_clients` (Redis Set).
   - Для каждого user_id:
     - Получить старое состояние из `state_store.get(user_id)`
     - Извлечь `card` и `bookings`
     - Использовать `ClientsRepository.upsert_client()` + `update_referral_info()`
     - Для каждой booking использовать `BookingsRepository.create_booking()` (с защитой от дубликатов по `id`)
   - Сохранять метаданные миграции (когда мигрировано, версия и т.д.)

3. **Защита от дубликатов**:
   - При создании booking проверять, существует ли уже запись с таким `id` в SQLite.
   - При upsert клиента — обновлять только если данные новее (по `updated_at` или просто перезаписывать).

4. **Порядок запуска**:
   - Сначала запустить в dry-run режиме.
   - Потом на staging / с бэкапом.
   - Запускать один раз после того, как write path стабилизируется.
